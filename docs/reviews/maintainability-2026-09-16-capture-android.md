- 범위: Payment Configuration 12개, Android Payment Ingestion 38개, Shortcut Ingestion 15개, Android Host/QuickEdit 26개, 합계 **91개 요구사항**입니다. 각 모듈의 requirements.md와 design.md를 읽고 실제 composition/bootstrap, Application, Firebase adapter, Web, Kotlin 경로를 대조했습니다.
- 이 단계에서는 보고서만 작성했습니다. 테스트 실행, 운영 데이터 조회, git 변경, 구현 변경은 하지 않았습니다. 아래 ‘확인’은 실행 경로와 정책 소유 위치를 정적으로 확인했다는 뜻이며 테스트 통과나 모든 입력의 정확성을 보증하지 않습니다.

## 판단

유지보수에 가장 큰 장애는 실제 구현의 계층 수 자체보다 **운영에서 실행되지 않는 과거 목표 구현이 실행되는 구현과 같은 src/Application/Port 이름으로 남아 있는 점**입니다. 카드 관리, Android Queue, 취소 매칭, Shortcut 저장·응답에서 같은 기능의 수정 후보가 둘 이상입니다. 이 부분을 제거하고 현재 흐름을 문서에 명시하는 편이 새 아키텍처를 추가하는 것보다 효과가 큽니다.

정상 결제 경로는 이미 합리적으로 최적화되어 있습니다. Android는 금융 파싱 없이 원문 admission과 암호화 WAL을 수행하고, 서버는 본인 카드·가맹점 규칙·원장 저장을 공통 경로로 처리합니다. 일반 Android 승인 하나에는 불필요한 상위 receipt를 생략하며, 새 QuickEdit은 서버 snapshot으로 표시하여 추가 거래 Query를 피합니다. 3인 가구라는 이유로 이 멱등·권한·WAL·원자 분할 경계를 없애면 얻는 이득보다 유실/중복 위험이 큽니다.

### R3. 기존 가맹점·메모 치환을 지우는 수정이 다시 이전 값과 병합됩니다 — 작은 기능 수정

시나리오: 규칙에 merchant='마트', memo='식비'가 저장되어 있고 편집 화면에서 두 값을 지운 뒤 저장합니다. 화면은 category만 보내고 서버는 기존 merchant/memo를 다시 남깁니다. 이후 결제에도 사용자가 지우려던 치환이 계속 적용됩니다. 이는 실행 경로의 입력/병합을 따라 확인한 정적 결함이며 실제 운영 데이터로 실행하지 않았습니다.

최소 개선안: mapping의 patch 의미를 한 곳에서 정의합니다. API 호출부가 부분 mapping을 보내는 경로가 있으므로 모든 mapping을 무조건 replacement로 바꾸지 않는 편이 안전합니다. **필드 미제공=유지, 제공된 빈 문자열=그 규칙의 해당 치환 제거**로 정하고, Web 편집 화면은 merchant/memo를 명시적으로 보냅니다. 서버 mapping patch normalizer는 빈 필드를 삭제 의도로 보존하여 현재 값에 적용하고, 최종 저장 모델에서는 키를 제거합니다. 이 변경은 ‘거래의 memo를 비우기’와 ‘규칙의 memo 치환을 제거하여 원문 memo 보존’의 의미를 구분해야 합니다.

영향은 Web 규칙 편집과 해당 command validation/mutation에 한정됩니다. 생성 규칙, 빈 mapping의 파서 memo 유지(MER-003), category-only 수정이 다른 필드를 보존하는 동작, stale version/claim 원자성 검증이 필요합니다. 최소 회귀는 기존 치환 2개 설정→편집에서 삭제→다시 조회와 새 결제의 원문 표시입니다.

### R4. 실제 취소 업무 정책이 Firebase 저장 adapter 안에 있고 별도 미사용 정책이 있습니다 — 후속 리팩토링

### 교차 검토 후 호환 필드 정리

canonical/legacy 과거 문서의 최상위 `category`·`categoryId`가 남으면, mapping의 category 치환을 삭제해도 호환 reader fallback에서 값이 다시 나타나는 경로를 추가로 수정했습니다. canonical writer는 두 최상위 alias를 제거하고 legacy writer도 잔존 `categoryId`를 제거합니다. legacy의 `category` mirror는 최종 mapping에 따라 저장·삭제합니다. AtomicStore의 기존 문서 해석은 최상위 `categoryId`와 `category`를 모두 읽어, 카테고리를 생략한 부분 수정에서 이전 값이 손실되지 않도록 했습니다.

실제 Firestore에 canonical/legacy × 최상위 category/categoryId 네 가지 문서를 seed하고, 실제 Household Command로 치환을 삭제한 뒤 같은 CaptureConfigurationQuery로 projection 재생성·재조회를 검증했습니다. 후속 메모 수정에도 삭제된 값이 되살아나지 않습니다. 별도로 category를 수정하지 않은 patch가 과거 categoryId를 canonical mapping으로 보존하는지도 확인했습니다.

최종 focused 결과는 관련 adapter **4개 파일/15개 테스트**, 실제 Firestore mapping suite **6개 테스트**, Functions test 타입 검사 통과입니다. 운영 데이터와 배포는 변경하지 않았습니다.
