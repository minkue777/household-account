# 유지보수성 리뷰: 가계부·지원 읽기 영역

소스 근거 링크와 행 번호는 분석 기준 커밋 `c57d776`에 고정합니다. 구현 후 결과는 문서 마지막 절에 구분합니다.

최초 검토일: 2026-09-16. 담당 모듈은 ledger, categories-budget, recurring-transactions, local-currency, reporting, home-preferences 6개이며 소유 요구사항 **54개**를 실제 Functions/Web 경로와 대조했습니다. 각 requirements.md/design.md를 읽고 bootstrap에서 실행 경로를 추적했습니다. 최초 분석은 읽기 전용으로 수행했으며, 이후 사용자 요청에 따라 2026-09-17에 아래 구현 결과의 로컬 수정과 검증을 진행했습니다. commit/push·배포·운영 데이터 조회는 하지 않았습니다.

다음 findings와 coverage는 수정 전 정적 유지보수성 분석입니다. 삭제한 구현의 경로와 라인은 분석 당시 근거이며 현재 실행 경로는 마지막 구현 결과와 각 모듈 design.md의 실행 경로 안내를 참고합니다. 표의 “확인”은 모든 예외의 완전 검증을 뜻하지 않습니다. 실제 실행한 테스트는 마지막 검증 표에 별도로 기재합니다.

### F2 — P2: 카테고리 사용 가능 판정을 소비 모듈의 bootstrap들이 각자 구현합니다

- 근거: [functions/src/bootstrap/commands/ledgerHouseholdCommandHandlers.ts](https://github.com/minkue777/household-account/blob/c57d7768714f99a065dd2f1bdeba7fc7d587984a/functions/src/bootstrap/commands/ledgerHouseholdCommandHandlers.ts#L188)는 root categories를 조회하고 isActive만으로 사용 가능 여부를 만듭니다. [functions/src/bootstrap/commands/recurringHouseholdCommandHandlers.ts](https://github.com/minkue777/household-account/blob/c57d7768714f99a065dd2f1bdeba7fc7d587984a/functions/src/bootstrap/commands/recurringHouseholdCommandHandlers.ts#L116)는 canonical/legacy 두 저장소를 직접 읽고 state=active, archived/archive-pending 판정을 별도로 구현합니다. Category의 판정은 [functions/src/contexts/household-finance/categories-budget/domain/policies/categoryCatalogPolicy.ts](https://github.com/minkue777/household-account/blob/c57d7768714f99a065dd2f1bdeba7fc7d587984a/functions/src/contexts/household-finance/categories-budget/domain/policies/categoryCatalogPolicy.ts#L68) 및 [functions/src/contexts/household-finance/categories-budget/application/categoryCatalogApplication.ts](https://github.com/minkue777/household-account/blob/c57d7768714f99a065dd2f1bdeba7fc7d587984a/functions/src/contexts/household-finance/categories-budget/application/categoryCatalogApplication.ts#L349)에 있습니다.
- 변경 시나리오: archive-pending 허용 범위, historical-display 용도 또는 canonical 전환 정책을 바꾸면 Category 외에 Ledger handler와 Recurring handler를 찾아 수정해야 합니다. 실제로 Ledger는 legacy boolean만, Recurring은 canonical state까지 읽어 판단 기준이 다릅니다. 현재 projection이 정상 동기화돼 있다면 두 결과가 같을 수 있으므로 현재 데이터의 오동작은 확정하지 않습니다.
- 개선: Category 소유의 작은 read reference 함수/adapter 하나가 canonical 우선/legacy 호환과 usable 판정을 담당하도록 하고 Ledger·Recurring에는 각자 필요한 typed 결과만 맞춰 주입합니다. 새로운 범용 framework나 네트워크 호출은 필요 없습니다. canonical/legacy/archived/archive-pending fixture를 그 경계에서 공유합니다.

### F3 — P2: 정기거래 Workflow가 Ledger 거래 모델·저장 형식·Event를 재정의합니다

- 근거: [functions/src/contexts/household-finance/recurring/domain/model/recurringProcessing.ts](https://github.com/minkue777/household-account/blob/c57d7768714f99a065dd2f1bdeba7fc7d587984a/functions/src/contexts/household-finance/recurring/domain/model/recurringProcessing.ts#L25)가 RecurringLedgerTransaction을 별도 소유하고 [functions/src/contexts/household-finance/recurring/domain/policies/recurringProcessingPolicy.ts](https://github.com/minkue777/household-account/blob/c57d7768714f99a065dd2f1bdeba7fc7d587984a/functions/src/contexts/household-finance/recurring/domain/policies/recurringProcessingPolicy.ts#L125)가 거래와 TransactionRecorded Event를 만듭니다. [functions/src/adapters/firebase/recurring/firebaseRecurringFinanceUnitOfWork.ts](https://github.com/minkue777/household-account/blob/c57d7768714f99a065dd2f1bdeba7fc7d587984a/functions/src/adapters/firebase/recurring/firebaseRecurringFinanceUnitOfWork.ts#L337)가 canonical/legacy Ledger 문서를 직접 만들며, [functions/src/adapters/firebase/recurring/firebaseRecurringFinanceUnitOfWork.ts](https://github.com/minkue777/household-account/blob/c57d7768714f99a065dd2f1bdeba7fc7d587984a/functions/src/adapters/firebase/recurring/firebaseRecurringFinanceUnitOfWork.ts#L460)의 ledgerDocument는 [functions/src/adapters/firebase/ledger/firebaseLedgerCommandRepository.ts](https://github.com/minkue777/household-account/blob/c57d7768714f99a065dd2f1bdeba7fc7d587984a/functions/src/adapters/firebase/ledger/firebaseLedgerCommandRepository.ts#L101)와 별도 mapper입니다.
- 변경 시나리오: Ledger 공통 저장 metadata, read schema 또는 TransactionRecorded payload를 바꾸면 정기일정 기능을 바꾸지 않아도 Recurring Domain과 Firebase UoW를 수정해야 합니다. 수동 경로만 바꾸면 정기 거래는 별도 형식으로 계속 생성됩니다. 현재 두 mapper가 recurring 전용 필드를 가지는 사실 자체는 문제가 아니며, 공통 원장 계약의 소유권이 둘로 나뉜 점이 문제입니다.
- 개선: Ledger가 recurring posting을 검증하고 persistence-neutral 거래/Event 의도를 반환하는 작은 participant를 제공합니다. 기존 Finance UoW는 execution·receipt·Ledger write·Outbox를 같은 transaction으로 계속 commit합니다. **원자성·결정적 execution key·creator 보존을 줄이거나 두 transaction으로 나누면 안 됩니다.** 이 작업은 작은 미사용 코드 정리와 별도 변경으로 다루는 편이 안전합니다.

### F4 — P2: 예산 계산의 별도 구현에서 0원 예산의 의미가 갈라져 있습니다

- 근거: 실제 [web/src/components/BalanceCards.tsx](https://github.com/minkue777/household-account/blob/c57d7768714f99a065dd2f1bdeba7fc7d587984a/web/src/components/BalanceCards.tsx#L62)는 budget이 null인 경우만 제외하여 budget=0 카테고리의 지출도 잔여 예산에서 뺍니다. 반면 [functions/src/contexts/household-finance/categories-budget/domain/calculations/monthlyBudgetCalculator.ts](https://github.com/minkue777/household-account/blob/c57d7768714f99a065dd2f1bdeba7fc7d587984a/functions/src/contexts/household-finance/categories-budget/domain/calculations/monthlyBudgetCalculator.ts#L42)는 budget>0인 경우만 budgetedCategoryExpense에 포함합니다. 이 서버 계산은 [functions/src/contexts/household-finance/categories-budget/application/queries/getMonthlyBudget.ts](https://github.com/minkue777/household-account/blob/c57d7768714f99a065dd2f1bdeba7fc7d587984a/functions/src/contexts/household-finance/categories-budget/application/queries/getMonthlyBudget.ts#L83)에만 연결되며 production bootstrap 소비를 찾지 못했습니다.
- 구체적 차이: 예산 0원 카테고리에 지출 1,000원이 있는 동일 입력이면 실제 홈 계산의 잔여 예산은 -1,000원, 서버 계산은 0원입니다. [web/src/components/CategorySummary.tsx](https://github.com/minkue777/household-account/blob/c57d7768714f99a065dd2f1bdeba7fc7d587984a/web/src/components/CategorySummary.tsx#L61)의 “0원은 진행률 없음”은 표시 정책이며 잔여 예산 포함 여부와 구분해야 합니다.
- 영향: 향후 홈을 서버 Budget Query로 연결하거나 테스트 대상을 바꾸는 리팩토링이 계산 결과까지 바꿀 수 있습니다. 어느 값이 제품 정책상 맞는지 이 보고서에서 새로 결정하지 않습니다.
- 개선: 당장은 실제 Web 동작을 유지한 채 예산 포함 판정과 진행률 판정을 이름 있는 순수 함수로 분리하고, 미사용 서버 경로를 유지할 명확한 소비자가 없다면 F1에서 정리합니다. 정책 통일로 결과를 바꾸는 작업은 별도 요구사항 확인 후 진행합니다.

## 유지할 경계와 단순성

- 월 원장/잔액을 app shell이 구독하고 파생 화면이 소비하는 구성은 route마다 독립 조회를 추가하는 것보다 수정 파급과 읽기 비용이 작습니다.
- Ledger 구조 변경의 선택 ID 조회, server version 재검증, provenance 보존, receipt 및 Outbox는 금융 데이터 정합성의 실제 보호입니다. “3명만 사용”한다는 이유로 순차 client write로 바꿀 대상이 아닙니다.
- Category archive가 과거 원장을 수정하지 않고 Recurring/merchant 설정만 remap하는 책임 분리는 좋습니다.
- Local Currency의 DTO intake·관측 순서 정책·유형별 저장·독립 branch receipt는 한 책임 안에 모여 있습니다. Home 최초 선택의 같은 transaction 참여도 명시적 계약이라 결합 그 자체를 문제로 보지 않습니다.
- Theme은 실제 Web에 단순하게 남기는 것이 맞습니다. 5개 테마에 서버 Domain/Port 구현을 병행할 실익을 확인하지 못했습니다.
- 범위가 제한된 검색·통계와 세션 메모리는 현재 가구 규모에 맞습니다. 데이터 증가/실측 없이 Elasticsearch, 영속 통계 Projection, 더 작은 페이지/복잡한 백그라운드 집계를 도입할 근거가 없습니다.

### 남은 범위와 비용

1. **카테고리 검증 조회 비용:** Ledger의 카테고리 검증이 필요한 명령은 legacy 한 번에서 canonical+legacy 두 번의 병렬 조회로 늘어납니다. 메모 수정·삭제처럼 카테고리를 검증하지 않는 경로는 계속 조회를 생략합니다. 현재 CategoryCatalogStore도 두 집합을 합치며 전체 canonical 이관 완료를 확인할 marker가 없어 canonical이 있다는 이유만으로 legacy를 생략하면 부분 이관 데이터를 놓칩니다. 이번에는 3인 가구 규모에서 단순한 공통 판정과 호환성을 택했습니다. 향후 감축한다면 canonical 완료 계약을 먼저 마련하거나 각 명령의 필요한 categoryId만 전달하는 작은 reference API로 전환한 뒤 partial migration fixture로 검증해야 합니다.
2. **Reporting 잔여 목표 Query:** boundedReportingQuery, boundedAssetStatisticsQuery, getLedgerStatistics, asset snapshot continuity, historicalAssetDimensions 및 action Controller는 아직 서버 fixture에서 계약을 검증하며 production 화면 경로가 아닙니다. 이번에 실제 Web으로 대응이 명확한 기간·카테고리 선택 검증만 이관했습니다. 잔여 정리는 fixture별 주장을 Web의 reportingReadAdapters/실제 page 테스트에 매핑하고, source checkpoint·정상 빈 결과·과거 owner 같은 계약 차이를 먼저 명시한 다음 대응이 확보된 가지를 순차 제거해야 합니다. 현재 UX나 저장소 일관성 수준을 조용히 바꾸는 전면 이관은 하지 않았습니다.
3. **정기거래 경계:** 이번 변경은 저장 형식과 생성 의도의 소유 위치를 단일화한 작은 participant입니다. 새로운 transaction 조정 framework나 별도 Ledger command 호출을 도입하지 않았습니다. 향후 posting 검증을 확대하더라도 기존 UoW의 원자 commit을 유지해야 합니다.
