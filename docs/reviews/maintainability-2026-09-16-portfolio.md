## 범위와 판정 기준

포트폴리오, 보유종목·시장 데이터, 자산 자동화, 배당, 외부 연동·운영의 requirements.md와 design.md 10개 전체를 읽고, 소유 요구사항 45개를 현재 Functions/Web 진입점부터 대조했습니다. 초기 분석은 읽기 전용으로 수행했습니다. 이후 사용자가 구현을 승인하여 2026-09-17에 아래 수정 결과를 추가했습니다. 아래 발견과 coverage의 “일치”는 분석 시점의 정적 대조이며, 수정 후 검증 결과는 마지막 절에 구분했습니다. commit/push/배포와 운영 데이터 조회는 수행하지 않았습니다.

파일 길이와 파일 개수 자체를 문제로 판단하지 않았습니다. 실제 수정 시 어느 정책을 바꿔야 하는지, 그 수정이 다른 모듈에 얼마나 번지는지, 사용하지 않는 구현과 중복 계산을 줄일 수 있는지를 기준으로 보았습니다. 금융 정확성에 필요한 version 검사, 원자 commit, 멱등 실행, 권한과 마지막 정상 시세 보존은 유지해야 합니다.

핵심 결과는 실제 실행 경로와 명세형 Application이 병존하여 정책 소유 위치가 불명확하고, 화면·공급자 정규화·오류 분류에 이미 서로 다른 동작이 생겼다는 점입니다. 3인 가구 규모에서는 새 범용 플랫폼을 추가하기보다 실제 진입점에 정책을 모으고 읽기 범위를 줄이는 것이 적절합니다.

## 좋은 경계와 유지해야 할 복잡성

- 사용자 명령과 예약 시세 갱신은 같은 runtime 평가 정책을 사용하고, 공급자 조회는 transaction 밖에서 수행합니다. Position+Asset+receipt+Outbox를 같이 저장하는 경계는 금융 불일치를 막으므로 모듈 분리 때도 유지해야 합니다.
- Catalog는 Cloud Storage publication과 Web IndexedDB/memory 읽기를 분리하고 last-good를 유지합니다. 3인 가구라도 공개 시장 목록 전체를 검색하므로 기기 검색·일일 snapshot은 사용자 수만으로 과대 설계라고 할 수 없습니다.
- 자동화는 화면 방문에서 분리되었고 due Plan만 읽으며 월 execution과 잔액을 원자 반영합니다. 월말·과거 revision·삭제 기간 제외·멱등 claim은 실제 요구사항에 대응합니다.
- 배당은 stable event identity와 paid 불변을 저장 경계에서 지킵니다. 신규 discovery와 기존 lifecycle 분리는 적절하며, F5는 이 경계를 끝까지 적용하지 못한 부분입니다.
- 공통 tracked runner, lease fencing, checkpoint와 독립 monitor는 Scheduler의 at-least-once·미시작 장애를 다룹니다. 이를 단순 cron callback 하나로 줄이면 요구사항을 잃습니다.
- Billing은 source→순수 계산→최신 성공 snapshot으로 분리되어 있습니다. Admin 조회가 BigQuery를 직접 호출하지 않는 작은 구조가 적절합니다.

- source graph에서 미도달이라고 바로 지우지 않습니다. 운영 script·migration·test·public type re-export 사용 여부를 함께 확인한 뒤 미사용 Application만 정리해야 합니다.

### 교차 리뷰 후 추가 보정

- 공급자 공시 번호가 없는 구형 이벤트는 HTTP 호출 없이 attempts=0/no-data로 종료합니다. 이 결과를 정상 공급자 관측으로 기록하면 실제 KIND 실패 streak와 경보가 지워질 수 있어, `recordProviderResult`는 attempts=0인 로컬 판정을 제외합니다. 실제 `KindEtfDividendDisclosureSource`와 `FirebaseDividendProviderObservation`을 연결한 테스트에서 HTTP 403 장애가 4회 누적되어도 구형 이벤트가 경보를 닫지 않음을 확인했습니다.
