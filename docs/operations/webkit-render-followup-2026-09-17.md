# WebKit 검색·통계 성능 후속 검증

## 최종 반영 범위

- 검색창 overlay의 `backdrop-blur-sm` 한 클래스만 제거합니다. 배경 가리개·크기·배치·검색 범위·결과 합계는 유지합니다.
- CI의 선택적 단계 진단에 16ms timer 간격 관찰을 추가합니다. 제품 코드에 timer나 로그를 추가하지 않습니다.
- `web-e2e` job의 Firebase Emulator 실행 파일 다운로드를 캐시합니다.

배당 조회를 Lite로 바꾸는 후보도 구현·검증했지만, 같은 runner에서 측정한 개선이 작고 분산과 겹쳐 채택하지 않았습니다. 해당 제품 변경·명세 변경·후보 전용 테스트는 이번 commit에서 제외합니다. 검색·통계의 성능 기준과 측정 종료 조건은 변경하지 않습니다.

## 출발점: 정식 CI의 네 가지 실패

`c835a258dc9cf79509f6a80d922e09e7de47059c`의 [CI 35175517320](https://github.com/minkue777/household-account/actions/runs/35175517320)은 기능 E2E 92개를 모두 통과했지만 성능 예산은 실패했습니다. 본 측정 462개와 준비 실행 66개가 완전하며 나머지 Web, Functions, Android, Android instrumentation job은 성공했습니다.

| WebKit 지표 | 전체 본 표본 ms | 중앙값 / 기준 ms |
|---|---|---:|
| 첫 검색 입력 → 결과 | 791, 1021, 801, 725, 722, 726, 764 | 764 / 500 |
| 검색 열기 → 입력·결과 | 842, 1069, 837, 755, 770, 761, 807 | 807 / 500 |
| 지출통계 재진입 | 389, 474, 399, 468, 448, 428, 434 | 434 / 400 |
| 자산통계 재진입 | 405, 404, 420, 418, 414, 506, 478 | 418 / 400 |

첫 검색은 DOM 조건 충족까지 286~387ms, 그 뒤 기존 종료까지 419~634ms가 남았습니다. 지출통계 재진입의 DOM은 10~16ms에 준비되지만 마지막 canvas 그리기는 334~419ms였습니다. DOM 충족 시각으로 화면 표시 완료 판정을 앞당기지 않습니다. CI마다 CPU가 EPYC 9V74 또는 7763으로 달라져 서로 다른 실행 간 수치 차이를 제품 효과로 단정하지 않습니다.

## 검색 병목과 채택 근거

[Linux 진단 35179558366](https://github.com/minkue777/household-account/actions/runs/35179558366)은 제품 소스 `c835a25`를 유지하고 여섯 CSS 조건을 세 번씩 순환 비교했습니다. 준비 표본 4개와 본 측정 72개가 완전합니다. 모든 backdrop을 제거했을 때 첫 검색 중앙값은 851→442ms였지만 자산통계는 419→424ms로 효과가 없었습니다. 검색 목록 containment와 모달 높이 고정은 검색어 변경을 악화시키는 조건이 있어 채택하지 않았습니다.

원래 첫 검색의 최장 rAF 간격은 805, 415, 539ms였고 backdrop 제거 시 80, 100, 82ms였습니다. 원래 측정 구간 내부 timer의 최장 간격은 28, 93, 130ms로, 긴 프레임 간격 동안에도 JavaScript가 계속 실행됐습니다. 따라서 검색 지연의 큰 부분은 배경 합성·프레임 처리와 관련 있으며 업무 로직의 동기 계산만으로 설명할 수 없습니다.

[영역별 진단 35180343320](https://github.com/minkue777/household-account/actions/runs/35180343320)은 배당 Lite 후보를 모든 조건에 동일하게 적용하고 검색창·홈 카드의 backdrop만 분리했습니다. 같은 build·EPYC 7763 runner에서 네 조건을 각각 네 번 측정했고 순서를 한 칸씩 바꿨습니다. 준비 표본 4개와 본 측정 64개가 완전하며 실패는 없습니다. 아래는 중앙값 ms입니다.

## 배당 조회 후보를 제외한 이유

자산 통계의 보유 종목·배당 스냅샷·배당 이벤트 세 입력을 기존 `firestoreServerReadModel`의 Lite로 바꿔 검사했습니다. 가구 조건·연도·문서 변환·병렬 실행·세션 격리·실패 전파를 유지한 후보이며 관련 43개 단위 테스트와 production build를 통과했습니다. 로컬 두 브라우저에서도 네 지표를 7회씩 실행해 본 표본 56개와 준비 표본 8개가 완료됐습니다. 그러나 이 사실만으로 속도 개선을 입증할 수는 없습니다.

[직접 비교 35180796206](https://github.com/minkue777/household-account/actions/runs/35180796206)에서는 같은 build·EPYC 7763 runner 안에서 진단 전용 스위치로 조회 SDK만 번갈아 선택했습니다. 두 조건 모두 검색창 backdrop을 제거했습니다. 네 번씩 측정했으며 준비 표본 8개와 본 측정 32개가 완전합니다.

| 자산통계 재진입 방식 | 전체 본 표본 ms | 중앙값 ms |
|---|---|---:|
| 기존 realtime SDK | 609, 547, 537, 526 | 542 |
| Lite 단발 서버 조회 | 553, 510, 592, 501 | 531.5 |

중앙값 차이는 10.5ms이고 범위가 겹칩니다. 사용자 체감 개선의 근거가 부족하며 오프라인 캐시 대체 동작도 달라지므로 제품에는 기존 조회 방식을 유지합니다. 진단 스위치는 main에 포함하지 않습니다.

## 실패 기록과 남은 문제

이전 [영역별 진단 35180022273](https://github.com/minkue777/household-account/actions/runs/35180022273)은 준비 표본 4개와 본 측정 성공 23개 후 자산통계에서 30초 timeout으로 중단됐습니다. 배당은 `조회 중`, 현재 자산은 서버 응답 대신 `마지막 기록 자산 7,699,000원`으로 남았습니다. 두 canvas는 그려졌지만 세 번째 배당 canvas와 정확한 현재 합계는 준비되지 않았습니다. 완료된 Promise를 UI가 잃어버리는 분기는 찾지 못했으나 입력별 완료 기록이 없어 단일 원인을 확정하지 못했습니다.

이 실패를 삭제하거나 성공 표본으로 바꾸지 않습니다. 이후 직접 비교에서는 기존 방식과 Lite 방식 모두 완료됐으므로, 이 한 번의 timeout이 조회 방식 변경으로 해결됐다고 보고하지 않습니다. 통계 재진입의 400ms CI 중앙값 기준 초과도 여전히 남은 문제입니다. 검색 개선만으로 전체 CI 해결을 선언하지 않습니다.

## 측정 및 CI 준비

기존 선택적 `PERFORMANCE_PHASE_DIAGNOSTICS`에 16ms timer의 최장 간격과 구간을 기록합니다. 완료·취소·시간 초과 때 정리하며, 관찰 확정은 기존 종료보다 늦을 수 있으므로 timer 구간을 `startAt`/`endAt`과 비교해야 합니다. 시작 이벤트, 종료 계산, 차트 안정 확인, 예산, 7회 표본 기준은 그대로입니다. 관찰 코드 자체가 무비용이라고 주장하지 않습니다.

정식 `web-e2e`에는 `~/.cache/firebase/emulators` 실행 파일만 캐시합니다. 실제 wrapper가 쓰는 Firebase CLI 버전을 고정한 Web lockfile 해시와 OS가 모두 같을 때만 재사용합니다. DB, Functions 프로세스·메모리, fixture, node_modules는 포함하지 않습니다. 동일 다운로드를 줄이려는 변경이며 절감 시간은 아직 측정하지 않았습니다. 기존 Functions·Next 빌드 재사용도 유지합니다.

검색 결과 범위·카드 검색·세션 변경 등 기존 검색 테스트 42개가 통과했습니다. 배당 후보를 제외한 최종 운영 소스의 production build·타입 검사·배포 산출물 검사도 통과했습니다. 채택하지 않은 배당 후보의 검증을 최종 main의 전체 CI 통과로 대신하지 않습니다. 최종 main SHA의 정식 CI는 독립적으로 후속 확인합니다.
