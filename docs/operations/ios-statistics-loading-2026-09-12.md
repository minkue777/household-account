# iPhone 첫 화면과 통계 조회 지연 개선

## 운영에서 확인한 사실

사용 환경은 iOS 18.7.8의 홈 화면 PWA다. 사용자는 화면 틀 이후 데이터까지 약 2초, 지출 통계 약 20초, 자산 통계 약 10초의 대기를 보고했다.

9월 11일 Firebase 배포 이후의 `clientStartup` 로그를 읽기 전용으로 조회했다. 9월 12일 09:23~09:27 KST의 iPhone 표본 6건은 1,203 / 3,851 / 4,989 / 5,124 / 5,470 / 5,539ms이며 중앙값은 5,056.5ms다. 같은 날 09:28의 Android 표본 1건은 1,320ms다. 첫 화면의 모든 최신 데이터가 그려진 종료점이며, 화면 틀 이후의 구간이나 통계 진입 시간을 따로 측정한 값은 아니다. 표본이 작아 기기 전체의 평균 성능으로 일반화하지 않는다.

현재 가구에 대해 문서 본문 없이 Firestore `count()`로 조회 규모를 확인했다.

| 원천 | 문서 수 | 기존 순차 조회 | 변경 후 순차 조회 |
|---|---:|---:|---:|
| 현재 월 원장 | 82 | 첫 월 구독 | 첫 월 구독 |
| 기본 1년 지출 통계 원장 | 1,729 | 4회 | 1회 |
| 기존 자산 이력 | 2,074 | 5회 | 1회 |
| canonical 자산 일별 snapshot | 52 | 1회, 기존 이력과 병렬 | 1회, 기존 이력과 병렬 |

지출 원천 수에는 조회 후 표시 여부·거래 유형을 판정하는 문서도 포함된다. 기간은 2025-10-01~2026-09-30이다. 각 count의 Admin API 응답은 96~99ms였지만, 이는 클라이언트에서 전체 문서를 내려받는 시간과 비교할 수 없다. 거래·금액·사용자 식별자는 조사 결과에 저장하지 않았다.

## 확인한 대기 경로

화면과 통계의 업무 로직은 WebView와 PWA가 공유한다. 차이는 브라우저 엔진과 Firebase 초기화 설정에 있다. Android는 Firestore memory cache, iPhone PWA는 multiple-tab IndexedDB persistent cache를 사용했다.

설치된 Firebase SDK의 IndexedDbPersistence는 primary lease를 5초 동안 유효하게 취급하고 4초마다 다시 확인한다. 이전 실행이 종료 정리를 하지 못해 최근 owner 레코드가 남으면 새 실행은 서버 구독 시작부터 기다릴 수 있다. query의 로컬 캐시 처리도 서버 구독 이전에 수행한다. 저장된 query target이 있으면 재사용하므로 매번 모든 문서를 로컬에서 검색한다는 뜻은 아니다.

실제 SDK와 Firestore Emulator에서 잔존 owner 레코드만 합성해 이 경로를 재현했다. 실제 iPhone의 프로세스를 강제 종료한 실험은 아니다.

| Chromium + 동일 persistent/long-polling 설정 | 첫 월 서버 결과 |
|---|---:|
| 정상 owner 상태 | 74~85ms |
| 2.5초 전 owner가 남은 조건 | 4,076ms |
| 방금 기록된 owner가 남은 조건 | 8,097ms |

따라서 수 초 대기를 만드는 SDK 경로는 확인했지만, 운영 표본의 모든 지연이 이 원인이라고 확정하지 않는다. iOS 18.7.8을 [Safari 26.4 이후의 별도 streaming 결함](https://github.com/firebase/firebase-js-sdk/issues/9789)과 동일시하지 않는다. long-polling 자체에는 이 4초 lease 재확인 타이머가 없다.

## 변경

- iPhone 홈 화면 PWA의 Firestore도 Android와 같은 memory cache를 사용한다. 이전 IndexedDB를 삭제하거나 다른 탭의 소유권을 빼앗지 않는다. 기존 iPhone long-polling 설정은 유지한다.
- Firebase Auth의 영속 저장소와 UID별 세션·가구 metadata 복원은 유지한다. 첫 월 원장·카테고리·지역화폐는 기존대로 첫 서버 snapshot부터 표시한다.
- 지출·자산 이력의 페이지 크기를 500에서 5,000으로 늘린다. 페이지 수 상한은 100에서 10으로 바꿔 기존 원천별 50,000건 한계를 유지한다. 날짜 조건·정렬·cursor·실패 처리·세션 격리·모든 페이지 완료 후 합계 표시를 유지한다.
- 별도 endpoint, 주기 조회, 재시도, timeout 증가, 새 캐시 계층은 추가하지 않는다.

memory cache는 실행 간 Firestore resume token을 보존하지 않아 재실행 시 서버 재전송이 늘 수 있다. 일부 화면에서 SDK 캐시를 이용하던 오프라인 재실행 표시는 줄어든다. 온라인 서버 우선인 첫 홈, 별도로 저장하는 자산 화면 snapshot, Auth 로그인 유지와는 구분한다.

## 검증과 한계

실제 readModel과 매퍼를 호출하는 검사는 운영과 같은 1,729/2,074건의 1회 조회, 5,000건 경계의 다음 페이지, 중간 실패·세션 변경·상한 초과와 전체 완료 전 결과 미노출을 확인한다.

iPhone WebKit E2E는 실제 Auth·Functions·Firestore를 연결해 재실행 후 로그인 유지, 기존 거래·카테고리, 앱이 닫힌 사이 변경된 최신 지역화폐 잔액, 첫 홈 완료 mark를 확인한다. Auth IndexedDB는 열고 Firestore IndexedDB는 열지 않는 것도 관찰한다. 기존 timeout이나 화면 결과 검증을 완화하지 않는다.

집중 단위 검사 4개 파일·37개와 통계 캐시를 포함한 별도 집중 검사 3개 파일·42개가 통과했다(검사 집합은 겹친다). 실제 Firebase와 연결한 WebKit 재실행 및 Chromium 지출·자산 통계 E2E 12개도 통과했다. 이 로컬 WebKit 재실행의 첫 홈 완료는 575ms였으나 합성 자료와 로컬 서버에서의 관찰값이며 실제 iPhone의 개선 수치가 아니다.

원격 CI와 배포 상태는 해당 commit의 Actions·Vercel 기록으로 확인한다. 로컬 SDK/Emulator 수치는 실기기의 개선 시간으로 사용하지 않는다. 운영 첫 홈 로그를 같은 기기에서 다시 수집하고 통계 진입의 체감 지연도 확인해야 실제 개선 폭을 확정할 수 있다.

## 같은 날 재측정: 첫 홈 지연은 남아 있음

`86129f2` 웹 배포 후 12:52~12:53 KST의 iPhone 표본은 5,989 / 6,148 / 5,187ms다. 바로 뒤 12:54의 Android 표본은 1,146ms다. 사용자는 통계 페이지가 조금 빨라졌지만 첫 홈은 여전히 느리다고 보고했다. 앞선 캐시 변경이 이 첫 홈 지연을 해결했다는 근거는 없으며, 합성 lease 실험을 운영 지연의 확정 원인으로 해석하지 않는다.

가구의 카드 종류 필드만 읽어 확인한 현재 구성은 `LOCAL_CURRENCY_BALANCE + MONTHLY_REMAINING_BUDGET`이다. 이 구성에서는 연간 원장을 조회하지 않는다. 월 원장·카테고리·지역화폐 조회는 이미 병렬이며, 실제 지역화폐 카드 표시에는 설정과 잔액의 서버 응답이 모두 필요하다. 지표를 빨리 끝내기 위해 이 완료 조건을 제거하지 않는다.

남은 병목을 구분하기 위해 기존 `access.record-app-visit.v1`의 모바일 total에 선택적 `clientStartupTimingsMs`를 함께 보낸다. 고정된 15개 키의 숫자만 받으며, HTML 응답·웹 bootstrap·Auth·Membership·세션 준비·원장/카테고리/지역화폐 구독 시작 및 서버 완료·원장/전체 홈 paint의 Web Navigation 기준 도달 시각을 기록한다. 사용자 식별자, URL, 금액, 거래 내용, resource 이름은 포함하지 않는다. 화면 표시 전 추가 요청은 없고, 첫 홈 완료 시점에 복사한 값만 기존 접속 기록에 동봉한다.

관리자 상세에는 최신 한 표본의 총시간과 단계를 함께 표시한다. 병렬 단계는 합산하지 않는다. Android의 총시간은 기존 Activity 시계이고 단계는 Web Navigation 시계이므로 서로 다른 기준임을 표시한다. 최신 표본이 구버전이면 예전 표본의 단계를 끌어오지 않는다.

작은 실행 순서 개선으로 iPhone 알림 연결(FID/Messaging/worker/서버 등록)을 첫 원장 paint 직후에서 첫 홈 전체 paint 이후로 옮긴다. 홈 외 경로·실패 화면에서도 연결할 수 있는 기존 15초 fallback과 세션 변경 취소는 유지한다. 이 변경은 남은 홈 읽기와의 경합을 줄이며, 첫 원장 응답 자체의 지연까지 해결한다고 주장하지 않는다. Auth 저장 방식·Firestore 전송 방식·캐시 설정은 이번 후속 변경에서 그대로 유지한다.

새 필드를 수용하는 Firebase 서버를 먼저 배포하고 Web Git 배포를 진행한다. 필드를 보내지 않는 기존 앱과 total 집계는 계속 지원하며, 영구 데이터 migration이나 APK 변경은 없다. 새 단계 표본을 수집한 후 실제 지연 구간에 따라 다음 최적화를 결정한다.
