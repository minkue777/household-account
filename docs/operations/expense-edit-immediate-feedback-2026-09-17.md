# 메모·카테고리 저장의 즉시 화면 반영 복구

## 원인

`7af8c1084ad8346558d3abd35ed43404a78a983c`에서 저장 실패 시 초안을 보존하려고 공용 `ExpenseEditModal`의 닫기를 `await pendingSave` 뒤로 옮겼습니다. 메모·카테고리 모두 서버 응답까지 편집창이 남게 되어 사용자가 실제로 기다리게 됐습니다. 기존 `expenseService`의 낙관적 반영은 Command 호출 전에 실행되지만 편집창이 목록을 가리고 있었습니다.

입력 필드 자체에 새 debounce가 생긴 것은 아닙니다. Android 네이티브 Quick Edit는 별도 경로이며 이번 수정 대상이 아닙니다.

## 수정

- 일반 저장은 Command를 시작하면서 편집창만 숨겨 기존 낙관적 목록 변경을 바로 노출합니다. 폼 상태는 서버 응답까지 해당 편집 인스턴스에 남습니다.
- 성공하면 부모의 편집 선택을 정리합니다. 실패하면 기존 오류 안내를 확인한 뒤 같은 초안을 다시 표시합니다. 서버 거절 시 목록 원복은 기존 서비스가 담당합니다.
- 다른 거래·날짜·가구·페이지로 이동해 편집 인스턴스를 벗어나면 이전 응답이 새 편집창을 닫거나 초안을 덮지 않습니다. 네 편집 진입점은 작은 공용 `useExpenseEditor` 훅으로 사용자의 선택마다 새 key를 발급합니다. 같은 거래를 곧바로 다시 열어도 이전 저장에 묶이지 않습니다. 수입 요약에도 가구 경계를 둡니다.
- 통계 화면의 카테고리 목록 닫기는 요청 시점에 처리하고, 비동기 완료 후 다른 편집 상태를 변경하는 부모 코드를 제거합니다. 통계 데이터 자체는 기존처럼 서버 확정으로 갱신합니다.
- 삭제는 기존처럼 서버 성공까지 편집창을 유지합니다. 새 전역 초안 저장소, 재시도 타이머, 서버 변경은 추가하지 않습니다.

## 검증

수정 전 새 회귀 검사 18개 중 11개가 실패했고, 수정 후 같은 18개가 통과했습니다. 서버 Promise를 보류한 상태에서 편집창이 사라지는지, 오류 안내 확인 뒤 초안·카테고리·기억 선택이 복구되는지, 이전 요청이 다른 편집창에 간섭하지 않는지 검증합니다.

최종 관련 Web 검사는 7개 묶음의 88개가 통과했습니다. 통계에서 새 거래를 편집하는 동안 이전 저장이 끝나는 경우와, 동일 거래를 다시 여는 경우의 성공·실패 경합을 포함합니다. TypeScript 검사도 통과했습니다.

실제 브라우저 E2E는 `executeHouseholdCommand` 요청을 보류합니다. 서버 문서는 아직 변경되지 않았는데 편집창이 사라지고 목록의 메모·카테고리가 바뀌는지 확인한 뒤 요청을 해제해 실제 Emulator 문서와 버전 증가를 검증합니다. 가짜 성공 응답이나 고정 시간 판정을 사용하지 않습니다.

첫 관련 E2E 실행은 11개 중 10개가 통과하고, 저장 직후 같은 거래를 다시 여는 기존 검색 검사가 실패했습니다. 거래 ID만 key로 쓰던 구현을 선택별 인스턴스로 수정한 뒤, 운영 Web 빌드와 실제 Firebase Emulator에서 즉시 반영·검색 수정·동일 거래 재편집의 3개 E2E를 재실행해 모두 통과했습니다. 기존 검색 검사의 대기를 늘리거나 서버 성공까지 기다리도록 변경하지 않았습니다.

기존 성능 측정의 UI 완료 조건과 서버 확정 측정은 유지합니다. 성능은 계속 보고 전용이며, 참고선이나 측정 기준을 바꾸어 이번 지연을 감추지 않습니다.

배포 대상은 Vercel Git 자동배포의 Web입니다. Firebase·Android APK의 실행 코드는 변경하지 않습니다.
