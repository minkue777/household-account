# 핵심 기능 성능 최적화와 PASS/FAIL

이 문서는 v1 기준의 측정 이력입니다. 이후 강화한 기준과 추가 개선 결과는 [v2 성능 보고서](core-feature-performance-v2-2026-09-17.md)에 기록합니다.

기준선: [최초 반복 측정](core-feature-performance-2026-09-17.md). 제품 변경 범위는 전체 기간 검색, 자산 이력 조회, 통계 차트의 중복 계산·갱신입니다. UI·정확한 합계·조회 범위·세션 격리·최신성 정책·애니메이션을 유지합니다.

## 확인한 원인과 변경

- 같은 로컬 환경의 1회 구간 진단에서 Chromium 검색 SDK 조회는 1,676.6ms, 이후 변환·정렬은 5.6ms였습니다. 자산 이력 SDK 조회는 2,132.9ms, 이후 해석은 6.3ms였습니다. WebKit의 준비 실행 검색은 361ms/6ms, 자산 이력은 245ms/8ms였습니다. 이 진단은 정상 7회 성능 판정에 섞지 않습니다.
- Full Firestore SDK의 `getDocsFromServer`는 내부 listener와 원격 이벤트의 로컬 저장소 반영을 거쳐 반환됩니다. 일반 브라우저에서는 기존 IndexedDB 영속 캐시가 적용됩니다. SDK 대기 구간 전체를 네트워크 왕복 시간이라고 단정하지 않습니다.
- 전체 기간 검색과 자산 이력의 단발 서버 조회만 `platform/read-model/firestoreServerReadModel.ts`로 모았습니다. 설치된 Firestore Lite의 RunQuery를 사용하며 기존 FirebaseApp의 인증과 Firestore Rules가 유지됩니다. 자체 세션 메모리 캐시를 가진 두 조회에 별도의 영속 캐시 쓰기는 필요하지 않습니다. 실시간 구독과 일반 브라우저의 영속 캐시는 기존 경계에 남습니다. Full/Lite query·cursor를 섞지 않습니다.
- 검색용 모듈과 전체 원본은 검색창을 명시적으로 열 때 준비하며, 입력·다음 페이지가 같은 진행 중 요청을 공유합니다. 정렬은 원본당 한 번만 합니다. 검색창만 열고 닫으면 이전보다 조회가 추가되는 절충이 있습니다. 홈 진입만으로 전체 검색을 읽지는 않습니다.
- 지출 통계 재진입은 서버에서 다시 확인하되 결과의 모든 필드가 같으면 배열과 차트 옵션을 재사용합니다. 검증 완료만으로 애니메이션을 다시 시작하지 않습니다. 변경된 메모·카테고리·금액·합치기/분리 정보는 그대로 반영합니다.
- 자산 이력 문서를 한 번 해석하고 날짜순 결과에서 변동액을 계산합니다. 수익 차트는 각 기간마다 전체 과거 이력을 반복 탐색하지 않고 한 번 순회합니다.

임시 구간 진단 코드는 배포 소스에 남기지 않습니다.

## 판정 방식

예산의 단일 원본은 `tools/performance/budgets.mjs`입니다. 정상 실행은 지표마다 본 측정 7회 이상이 필요하며 다음을 모두 만족해야 PASS입니다.

1. 중앙값이 해당 지표의 기준 이내입니다.
2. 7회 중 6회가 반복 기준 이내입니다. 횟수가 다르면 `ceil(n × 6 / 7)`을 적용합니다.
3. 모든 표본이 개별 최대 허용 시간 이내입니다.
4. 실제 기능·데이터 검증과 표본 완전성 검증이 통과합니다.

기준 안에서 조금 느려졌다는 이유만으로 실패시키지 않습니다. 누락·중복·NaN·미등록 경로·7회 미만은 FAIL이며 느린 표본을 자동 제외하지 않습니다. 과거 Android 50.7초 표본의 제외는 최초 보고서에만 적용한 사용자 요청으로, 새 게이트의 예외가 아닙니다.

| 첫 검색 입력→결과 및 열기→결과 | 1500 | 2500 | 5000 |

Web은 33개 지표×2개 브라우저, Native는 5개 지표입니다. 준비 실행은 따로 보존하며 반복 실행 PASS를 최초 실행이나 실제 휴대폰 성능의 합격이라고 표현하지 않습니다. 차트에는 실제 애니메이션 완료가 포함됩니다.

## CI 실행 환경 기준

기본 `ux-v1`은 위 사용 목표를 그대로 적용합니다. CI에서만 명시적으로 선택하는 `github-hosted-v1`은 아래 항목의 고정 시간 기준을 사용합니다. 보고서에 **사용 목표 판정과 CI 판정을 둘 다** 남기므로 CI PASS가 사용 목표 PASS를 의미하지 않습니다. `CI=true`만으로 기준을 자동 변경하지 않으며 알 수 없는 프로필은 FAIL입니다.

| 환경·동작 | CI 중앙값 ms | 6/7 ms | 개별 최대 ms |
|---|---:|---:|---:|
| WebKit 홈 최초·재실행 | 1500 | 2000 | 5000 |
| WebKit 지출·계좌 상세 | 600 | 800 | 1000 |
| WebKit 메모·카테고리 반영 | 400 | 700 | 1000 |
| WebKit 지출 추가 반영 | 650 | 800 | 1000 |
| WebKit 지출 삭제 반영 | 500 | 700 | 1000 |
| WebKit 자산 첫 페이지 | 900 | 1200 | 5000 |
| WebKit 검색 다음 페이지·검색어 변경 | 400 | 650 | 1000 |
| Native 홈 Activity 재실행 | 4000 | 4500 | 5000 |
| Native Quick Edit 창 표시 | 1250 | 1500 | 2500 |
| Native Quick Edit 편집 준비 | 1500 | 1800 | 2500 |
| Native 저장 후 닫힘 | 1200 | 1500 | 2000 |
| Native 서버 저장 관측 | 1000 | 1500 | 5000 |

그 외, 특히 **Chromium 전체·첫 검색·통계는 사용 목표 그대로** 검사합니다. 개선 대상의 느린 기존 값에 맞춰 기준을 늘리지 않았습니다. 모든 프로필에서 50초 멈춤은 FAIL입니다.

근거는 [기존 전체 CI](https://github.com/minkue777/household-account/actions/runs/35162790485)의 두 브라우저 7회와 [후속 CI](https://github.com/minkue777/household-account/actions/runs/35163911281)의 Chromium·Native 7회입니다. 후속 WebKit은 fixture 준비 실패였으며 누락된 표본을 성능 성공 자료로 사용하지 않았습니다. Chromium 검색 중앙값은 두 실행에서 2872/2856ms, 자산 통계는 3940/3941ms로 반복됐습니다. 반면 CI WebKit의 지출 상세는 481ms, 추가는 524ms, 자산 첫 페이지는 683ms이며 같은 로컬 동작은 156/146/257ms였습니다. Native CI 홈은 3355ms, Quick Edit 표시는 1022ms였습니다.

이는 현재 실행 환경에 대한 **초기 고정 기준**입니다. WebKit·Native의 완전한 기존 CI 자료는 각각 한 배치이므로 장기간의 안정성이 이미 검증됐다고 주장하지 않습니다. CPU·OS·runner image·브라우저와 함께 후속 실행을 확인하고, 기준 변경은 원본과 이유를 문서화해야 합니다. 실행마다 배율이나 임계값을 자동 조정하지 않습니다. 로컬은 API 36/WebView 151, CI는 API 34/WebView 113이므로 차이는 하드웨어만의 차이도 아닙니다.

## 실행과 CI

기존 `npm --prefix web run test:performance`, `npm --prefix web run test:performance:android`를 사용합니다. Web reporter는 성능 FAIL을 Playwright 실패로 반환하고 Native runner도 보고서를 저장한 뒤 종료 코드 1을 반환합니다. 보고서 생성 실패도 성공으로 삼지 않습니다. 기존 CI job에서 그대로 실행하며 별도 성능 job을 추가하지 않습니다.

짧은 로컬 진단은 `PERFORMANCE_DIAGNOSTIC=true`, `PERFORMANCE_SAMPLES=1`을 명시해야 하며 DIAGNOSTIC으로 표시됩니다. 실제 기능이나 표본 오류가 있으면 진단도 실패합니다. CI에서는 진단 우회를 허용하지 않습니다.

각 실행의 OS·CPU·브라우저·표본과 초과 사유를 JSON/Markdown·GitHub summary에 남깁니다. CI 가상 기기의 시간과 실제 사용자 목표는 구분해서 해석해야 합니다. 예를 들어 같은 Android 홈 코드가 로컬 AVD에서는 중앙값 954ms, GitHub CI API 34/WebView 113 환경에서는 3,354.9ms였습니다. 이 차이만으로 실제 기기가 느려졌다고 결론내리지 않습니다. 환경 차이를 숨기기 위해 자동 배율이나 자동 임계값 완화를 적용하지 않습니다.

WebKit fixture 준비 단계에도 측정 단계와 동일한 iOS PWA 감지를 적용했습니다. 준비에서만 일반 브라우저 IndexedDB 경로를 타는 환경 불일치를 제거했습니다. 실제 로그인·가구 생성·서버 데이터 확인은 유지합니다.

## 최종 로컬 반복 측정
