## 변경

### 미국 종목 가격·환율 조회

- 가격 조회/관측 저장과 환율 HTTP 조회를 병렬로 시작한다.
- 같은 인스턴스에서 진행 중인 USD/KRW HTTP 요청 및 동일 관측값의 저장·fallback 조회를 공유한다. 완료된 영속 조회 결과까지 장기 캐시하지 않는다.
- 기존 환율 HTTP 캐시 5분, 장애 시 기존 관측값 사용, 다른 인스턴스가 저장한 최신 환율 선택은 유지한다.
- 가격과 환율을 동시에 요청해도 모든 공급자를 합쳐 실제 HTTP 동시 요청은 5개 이하로 제한한다. FIFO 대기 작업은 성공·실패 시 슬롯을 넘겨받는다.
- 갱신 서비스의 기존 target 동시성 5개, retry, lease 및 자산 버전 검증은 변경하지 않았다.

수정 전 HEAD의 어댑터와 수정 후 어댑터를 US 5종목, 고정 관측 시각, 동일한 가짜 공급자 및 저장소 지연으로 비교했다. 각 조건에서 모든 최종 quote 객체가 일치했고 최대 HTTP 동시성은 5개였다. source/rate 저장 지연은 각각 20 ms다.

| 조건 | HTTP 요청 전→후 | 환율 transaction 전→후 | 전체 완료 시간 전→후 |
| --- | ---: | ---: | ---: |
| cold, 가격·FX 각각 100 ms | 10 → 6 | 5 → 2 | 240 → 240 ms |
| cold, 가격 100 ms·FX 200 ms | 10 → 6 | 5 → 2 | 340 → 240 ms |

외부 호출 상한 때문에 cold 상태에서 다섯 번째 가격 요청은 슬롯이 날 때 시작한다. 따라서 균등한 지연에서는 요청 수가 줄어도 전체 완료 시간이 같을 수 있다. 환율이 더 느린 제어 조건에서는 약 29% 줄었으나 운영의 평균 5.8초가 같은 비율로 단축됐다는 뜻은 아니다. 동시 요청을 잠시 묶는 방식이므로 실제 환율 transaction 수는 각 종목의 완료 시점에 따라 달라진다.

### 홈의 필수 조회와 선택적 미리 읽기 분리

- `/income`, `/assets`, `/settings`, `/stats` 코드 준비와 인접 두 달의 원장 미리 읽기를 첫 홈 전체 표시 이후로 이동한다.
- 완료 신호가 없는 다른 진입 화면이나 읽기 오류에서도 작업이 영구 대기하지 않도록 15초 fallback을 둔다. 이 fallback은 홈 완료 표시나 측정값을 만들지 않는다.
- 세션/가구 변경, 읽기 세대 변경, unmount 시 예약과 취소 가능한 진행 작업을 정리한다.

### 관리자 대시보드 조회

가구원 조회는 가구 목록에만 의존하도록 묶었다. 이제 독립적인 Cloud Logging 조회나 다른 운영 집계가 끝나기를 기다리지 않고 가구원 조회를 시작한다. 가구별 결과 연결, 가구원 조회 실패의 전파, 로그 조회 실패 시 `unavailable` 처리는 유지한다.

## 추가 조사와 최적화

### 현재 가구의 시세 갱신 규모

2026-09-07 21:46 KST에 현재 가구의 런타임 상태를 읽기 전용으로 조회했다. 자산 17개(활성 16개), 보유 항목 17개 중 갱신 대상은 14개이며 고유 시세는 9개였다. 동일 종목 중복 그룹의 크기는 4, 2, 2개다. 대상은 국내 종목 13개와 실물 금 1개로, 이 시점의 대상에는 미국 종목이 없었다. 따라서 앞의 미국 종목 최적화를 이 가구의 현재 5.8초 지연 원인을 해결했다고 해석하지 않는다.

로더는 한 상태 조회에 22개의 문서/쿼리 읽기를 수행했다. 로컬 Admin SDK에서의 단일 읽기 전용 측정은 330 ms였으며 Functions handler 시간과는 다른 측정이다. 조회한 금액이나 종목명/코드는 보고서에 기록하지 않았다.

### 고유 종목별 시세 작업 배정

기존에는 50개 보유 항목마다 중복 제거 캐시를 다시 만들고 보유 항목마다 worker를 배정했다. 같은 종목의 응답을 기다리는 항목도 worker를 차지했으며, 50개 경계를 넘으면 다시 시세를 요청했다.

이제 한 실행에서 고유한 `market + instrumentCode`를 먼저 묶고 고유 시세에 worker를 배정한 후 모든 원래 항목에 결과를 적용한다. 공급자 동시성 5개, 항목별 최종 결과·실패 집계·부분 재시도·버전 검증을 유지한다.

| 제어 조건 | 요청 수 전→후 | 완료 시간 전→후 | 검증 |
| --- | ---: | ---: | --- |
| 현재와 같은 14항목·9종목, 응답 100 ms | 9 → 9 | 300 → 200 ms | 최종 상태·응답 동일, 최대 동시 5 |
| 동일 종목 51항목, 응답 100 ms | 2 → 1 | 200 → 100 ms | 최종 상태·응답 동일 |

첫 조건의 속도 차이는 공급자 요청 수 감소가 아니라 중복 항목의 worker 점유 제거에서 나온다. 실제 보유종목을 외부 시세 제공자에 보내는 추가 실측은 자동 승인 검토에서 외부 전송 승인이 명확하지 않다는 이유로 거절되어 실행하지 않았다. 위 비교는 외부 전송이 없는 가상 데이터/지연 실험이다.

### 자산 런타임 읽기

자산 목록·소유자 → canonical 보유 항목 분기와, 가구 ID만 필요한 legacy 보유 항목 읽기를 독립적으로 시작한다. 단일 자산 조회에서는 canonical/legacy 자산 문서를 `getAll`로 묶는다. 현재 상태와 최종 transaction 상태의 두 번 읽기 및 transaction 내부 검증은 유지한다.

설치된 Firestore SDK의 첫 읽기 후 transaction ID를 얻는 순서까지 포함한 제어 실험에서, legacy 조회 200 ms·다른 조회 100 ms 조건의 결과는 다음과 같다.

| 조건 | 읽기 RPC 전→후 | 완료 시간 전→후 |
| --- | ---: | ---: |
| 자산 17개 | 22 → 22 | 400 → 300 ms |
| 단일 자산 | 6 → 5 | 400 → 300 ms |

두 조건 모두 최종 상태가 동일했다. `getAll`은 RPC를 묶으며 과금되는 문서 읽기 수 자체를 줄이는 것은 아니다. 최신성·재시도 의미를 유지하기 위해 런타임 transaction을 `readOnly`로 바꾸지는 않았다.

### 지출 저장·항목 원복·방문 기록

- 일반 수정·삭제의 receipt와 현재 거래 사전 조회를 겹친다. receipt가 있으면 거래 읽기를 기다리지 않고 같은 결과를 반환하며, 늦은 거래 읽기 실패도 처리한다. 정상 경로의 사전 조회 대기는 두 단계에서 한 단계가 된다. replay에서는 거래 두 문서를 함께 읽는 추가 비용이 생기는 점과 반환 시간 개선을 구분한다.
- 기본 저장의 receipt·canonical·legacy 읽기를 같은 transaction의 `getAll` 한 번으로 묶어 전체 읽기 API 호출을 6회에서 4회로 줄인다. 버전·payload hash·가구·중복 실행 재검증은 유지한다.
- 항목 원복은 handler에서 원본·파생을 미리 읽던 중복을 제거하고, 서비스가 읽은 동일 원본에서 구형 클라이언트가 생략한 원본 버전만 보충한다. 파생 버전은 계속 클라이언트 값과 일치해야 한다. transaction의 대상 문서들도 일괄로 읽는다. 원본+파생 2개 조건에서 전체 읽기 API 호출은 16회에서 7회로 줄었다. 문서 수 감소와 RPC 일괄화 효과가 함께 포함된 수치다.
- 앱 방문 기록은 집계 문서와 영수증 문서의 순차 읽기 두 번을 같은 transaction의 `getAll` 한 번으로 묶는다. 방문 128개 이후 재실행, 다른 멤버의 독립 집계, 읽기 실패 시 영수증·집계 모두 미기록을 확인한다.

### 자산통계 배당 조회

배당 계산에 필요한 보유종목·배당 snapshot·배당 event 조회 세 개는 자산 이력에 의존하지 않는데, 기존에는 자산 이력 전체가 완료되고 차트가 mount된 후 시작됐다. 이제 검증된 동일 actor/epoch에서 이력과 함께 시작하고, 기존 차트 표시 조건이 충족될 때 page 내 Promise를 한 번 인계한다.

차트의 기존 표시 시점과 크기를 유지하므로 숨겨진 chart mount로 인한 레이아웃 문제를 만들지 않는다. 기간 변경으로 같은 source를 다시 mount하지 않으며, 연도 변경·포커스 갱신에는 새 조회를 수행한다. 다른 actor/가구/세션 세대 또는 폐기된 화면의 결과는 반영하지 않는다.

지출통계의 추가 조사에서는 이미 적용된 500개 페이지 읽기, 범위 캐시, 선형 집계 외에 현재 데이터 규모에서 입증할 수 있는 큰 병목을 찾지 못했다. 조회 제한이나 최신 데이터 완료 조건을 줄여 빠르게 보이게 만드는 변경은 하지 않았다.

### 공급자 상태 기록과 중복 시세 갱신 방지

시세 공급자 상태 기록은 성공한 경우에도 실패 시 사용할 이전 시세를 읽고 있었다. Firebase 어댑터의 해당 조회는 공급자 상태 문서 한 번, 연결된 이전 시세 문서 한 번으로 최대 2회 읽기인데 성공 분기에서는 결과를 쓰지 않았다. 이제 실패 분기에서만 이전 시세를 조회한다. 성공 시 건강 상태·복구 알림·새 시세 저장, 실패 시 마지막 정상 시세 유지, receipt replay는 그대로 검증한다. 상태 저장의 receipt·health 문서도 같은 transaction의 `getAll`로 묶는다.

추가로 시세 갱신의 `try`에서 원자 저장 Promise를 `await`하지 않고 반환하여 `finally`의 갱신 잠금 해제가 실제 commit보다 먼저 실행될 수 있었다. commit을 기다린 뒤 잠금을 해제하도록 보완했다. 실제 저장 직전까지 transaction을 정지시킨 제어 검사에서, 다른 UID의 갱신은 `MARKET_REFRESH_IN_PROGRESS`로 끝나고 추가 시세 조회가 0회임을 확인했다. commit 성공·실패 및 예상 밖 Promise 거부에서도 잠금은 한 번 해제된다.

이번 결과의 요청 수는 애플리케이션에서 호출하는 읽기 API/RPC 기준이다. 동일 transaction에서 묶인 문서 수, 공급자 호출 수, 기기 체감 시간은 서로 다른 지표이므로 직접 같은 비율의 비용·시간 절감으로 환산하지 않는다.
