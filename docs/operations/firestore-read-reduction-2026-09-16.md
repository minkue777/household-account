# 사용자 경험을 유지하는 Firestore 조회 절감

## 관측

- 2026-09-16 운영 Cloud Monitoring의 `firestore.googleapis.com/document/read_count`를 조회했다. 최근 24시간 구간은 약 24만~26만 회였다.
- 09:00~20:00 배당 예약 작업 실행 시간에는 시간당 약 19,200~20,100회, 대부분의 야간 구간에는 약 160회였다. 시간대 상관관계이며 함수별 청구액을 직접 측정한 값은 아니다.
- 운영 배당 문서 194건 중 현재 결정적 문서 ID 19건, 공시 ID가 있는 기존 문서 ID 27건, 공시 ID 없는 이관 기록 148건이었다. 거래 내용·개인 식별자·금액은 진단 로그에 기록하지 않았다.
- 공시마다 `findAnnouncement`와 `upsertAnnouncement`가 해당 가구의 배당 이력 전체를 각각 조회했다. 이미 저장된 공시를 매시간 확인할 때도 누적 이력 수에 비례해 읽기가 증가했다.

## 변경

- 현재 형식은 가구·공시 ID·종목으로 결정되는 문서 한 건을 직접 조회한다.
- 기존 문서 ID는 공시 ID 또는 alias로 조회하고 가구와 종목을 검증한다. 공시 ID가 없는 기록은 기존 공시 사실로 후보를 좁힌다.
- 지급 완료 보존, 정정·취소, 멱등 receipt, 최종 transaction 재조회는 유지한다. 운영 데이터 migration은 하지 않는다.
- 실시간 구독, 인증·권한 조회, 첫 화면 로딩, 통계 기간 전환, 매시간 배당 갱신 주기는 변경하지 않는다. 오래된 데이터를 허용하는 TTL 캐시를 추가하지 않는다.

## 검증과 효과의 범위

- 실제 Firestore Emulator 통합 테스트 13개 통과. 현재 형식, 기존 ID, alias, 공시 ID 없는 기록, 지급 완료 보존, 다른 가구·종목 분리, 정정과 상태 진행을 검증했다.
- 194건짜리 동일 가구 fixture에서 기존 공시 한 건의 확인·저장 전 탐색은 194 × 2 = 388문서 조회였다. 변경 후 실제 SDK 호출을 관측하여 Query 조회 0회, 문서 직접 조회 2회를 확인했다. 이 경로의 탐색 읽기는 약 99.5% 감소한다.
- receipt와 Event의 transaction 읽기는 위 수치에 포함하지 않았으며 그대로 남는다. 이관 기록은 추가 선별 쿼리가 필요하므로 같은 절감률을 모든 공시에 적용할 수 없다.
- 운영 환경에서 대상이 없는 테스트 식별자로 세 선별 쿼리를 실행하여 현재 인덱스에서 정상 응답함을 확인했다. 새 인덱스는 필요하지 않았다.
- 전체 일일 조회·청구액 감소율은 배포 후 같은 시간대의 운영 수치로 별도 확인해야 한다. 위 수치는 운영 전체 비용의 감소율이 아니다.

## 추가 후보

- 관리자 화면이 최신 예약 작업 상태를 표시할 때 최대 120개 실행 이력을 읽는 경로는 별도 최적화 후보다. 최신 작업별 쿼리에는 추가 복합 인덱스가 필요해 이번 변경에 포함하지 않았다.
- 배당 lifecycle와 연간 projection의 전체 조회는 이번 반복 탐색보다 작고 기존 기록 복구에 사용되므로 유지했다.
