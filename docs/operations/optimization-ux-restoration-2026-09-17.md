# 최적화 이후 검색·편집·통계 사용성 보완

## 변경

- 검색은 모든 일치 거래를 반환하고, 월을 펼칠 때 그 월만 렌더링한다. 50건 표시 cursor·더보기·별도 summary 상태를 제거해 월별 건수와 실제 목록을 같은 원본에서 계산한다.
- 원천은 문서 ID cursor로 요청당 5,000건씩 읽는다. 10,000건을 넘어도 검색하며, 마지막 페이지까지 성공해야 결과를 반환한다. 닫기·세션 변경 시 다음 페이지 조회를 중단하고 중간 실패를 부분 성공으로 표시하지 않는다.
- 수정 후 재조회는 기존 목록·펼친 월·스크롤을 유지한다. 저장 중 다른 검색어로 이동한 경우 이전 저장 완료가 새로운 결과를 덮지 않는다.
- 일반 수정·삭제 Command는 즉시 시작하되 서버 성공 후 편집창을 닫는다. 실패하면 초안을 유지하고 중복 제출을 막는다. 날짜 변경·마지막 거래 삭제로 원본 목록이 비어도 선택 객체를 보존하며, 사용자 날짜 이동·가구 변경은 이전 편집창을 폐기한다. 낙관적 목록 갱신과 실패 원복은 유지한다. 사용자의 직접 닫기는 허용한다.
- 자산 통계 재진입·앱 복귀는 같은 세션의 완료 캐시를 먼저 보여주면서 이력을 재확인한다. 기간 선택은 추가 조회 없이 처리하고, 재검증 실패에도 차트와 선택을 보존한다. 현재 총자산 실시간 구독과 일일 스냅샷 작성 정책은 변경하지 않는다.
- 모바일에서도 검색 버튼에 접근성 이름을 제공한다.

## 성능 검증 의미

없어진 `search.next-page` 대신 `search.expand-month`로 과거 월 클릭부터 해당 월 전체 표시까지 측정한다. 기존과 동일한 중앙값·반복·최대 허용 시간을 적용한다. 첫 검색은 이제 선택 월의 60건 전체를 검사한다(기존 50건). 나머지 성능 기준과 표본 수는 그대로다.

편집창은 서버 저장 성공 후 닫히므로 저장 클릭부터 목록 복귀까지의 시간에 서버 대기가 포함된다. 기존 지출 목록 반영·서버 확정 측정 경계와 허용 시간은 앞당기거나 완화하지 않는다. 과거 즉시 닫기 수치와 비교할 때 이 동작 차이를 고려해야 한다.

## 검증과 배포 범위

- 검색·편집·통계 집중 검사 8개 suite / 134개 통과.
- 최종 부모 경로 보완 후 편집 관련 3개 suite / 24개 재검증 통과. 실제 `LedgerPage → ExpenseDetail → ExpenseEditModal`을 사용한 날짜 변경·삭제 실패·날짜 이동·가구 변경 회귀 4개를 포함한다.
- 성능 판정·표본·HTML 보고서 검사 44개 통과.
- TypeScript, 요구사항 카탈로그, 아키텍처 검사 39개 통과. 최종 Web 프로덕션 빌드와 정적 HTML·CSP·Firebase SDK·서비스 워커 산출물 검사 통과.
- 모바일 Chrome·iPhone WebKit의 실제 브라우저 회귀 2개 통과. Firebase Emulator에 연결해 50건 초과 월의 전체 표시, 과거 거래 수정, 월·스크롤 보존을 확인했다. 전체 CI 성능 결과는 최종 push SHA의 별도 실행으로 확인한다.

Web 실행 코드만 바뀌므로 기존 main push의 Vercel Git 배포를 사용한다. Firebase 운영 데이터·Functions·APK는 변경하지 않는다. 대형 측정 결과나 로컬 검증 파일은 커밋하지 않는다.
