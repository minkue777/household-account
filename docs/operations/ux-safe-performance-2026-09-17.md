# 사용성을 보존한 검색·통계 성능 보완

## 확인한 CI 실패

제품 코드·성능 시나리오·통과 기준이 같은 세 실행을 비교했다. 기능 E2E와 성능 시나리오 실행은 모두 성공했고, 준비 실행 1회와 본 측정 7회가 완전했다. 아래 실패는 WebKit 시간 기준 초과다. Chromium의 같은 지표는 통과했다.

| CI | CPU | 검색 입력 | 검색 열기 포함 | 지출통계 재진입 | 자산통계 재진입 |
|---|---|---:|---:|---:|---:|
| [35182931398](https://github.com/minkue777/household-account/actions/runs/35182931398) | Intel Xeon 6973P-C | 442 | 466 | 261 | 320 |
| [35185237580](https://github.com/minkue777/household-account/actions/runs/35185237580) | AMD EPYC 9V74 | 710 | 739 | 435 | 407 |
| [35186452895](https://github.com/minkue777/household-account/actions/runs/35186452895) | AMD EPYC 7763 | 673 | 711 | 441 | 402 |

단위는 본 측정 중앙값 ms다. 검색 기준은 중앙값 500 / 6회 이상 800 이내 / 최대 1,500, 통계 재진입은 400 / 600 / 1,200이다. 마지막 실행은 네 지표 모두 중앙값만 초과했다. 앞선 실패 실행은 검색의 반복 기준도 초과했다. CPU가 달라 동일 하드웨어 비교가 아니며 CPU 종류만을 실패 원인으로 확정하지 않는다.

마지막 실패 실행의 검색 DOM 준비 중앙값은 Chromium 272.4ms, WebKit 278ms로 비슷했으나 측정 종료는 297.1ms와 673ms였다. WebKit 지출통계 재진입은 DOM 12ms, 모든 차트 최초 그리기 46ms, 마지막 그리기 382ms, 측정 종료 441ms였다. 데이터 준비 이후 그리기·프레임 구간에 큰 차이가 남아 있다. 실제 그리기 비용과 runner의 스케줄링 영향을 이 자료만으로 분리할 수는 없다.

## 유지하는 사용성

검색 월 전체 결과, 1만 건 초과 조회, 수정 후 월·스크롤 위치, 저장 실패 초안, 최신 데이터 재검증, 모든 차트와 범례, 150ms 차트 전환, 2px 배경 블러를 유지한다. 표시 건수 축소·추가 클릭·조회 생략·테스트 완료 시점 변경은 하지 않는다.

## 적용한 변경과 반복 측정

검색은 배경 블러와 변하는 결과 목록을 별도 형제 요소로 나누어 합성 범위를 분리한다. 통계는 같은 입력의 차트 재실행을 기본 `React.memo`로 생략하고, 콜백과 합계 계산의 참조를 유지한다. 자산은 전체 필드가 같은 확정 목록만 배열을 재사용하며 실제 금액·활성 상태 변경은 반영한다.

변경 전 `7af8c10` production 빌드를 먼저 완료하고 같은 로컬 WebKit·Firebase Emulator·7회 전체 경로로 후보를 비교했다. Windows/Ryzen 7 7800X3D, production Next.js, Playwright 1.62.0, worker 1개이며 브라우저·측정 종료점·fixture·표본 수는 같다. 각 실행은 33개 지표 × 본 측정 7회 + 준비 실행 1회 = 264개 표본이다. 단계 진단은 두 실행 모두 활성화했다.

| 동작 | 변경 전 중앙값 | 변경 후 중앙값 | 변경 후 7개 본표본 | 변경 후 최대 |
|---|---:|---:|---|---:|
| 검색 입력 → 결과 | 377 | 357 | 400, 357, 358, 353, 340, 371, 353 | 400 |
| 검색 열기 포함 | 401 | 381 | 425, 381, 383, 378, 363, 394, 379 | 425 |
| 지출통계 재진입 | 285 | 285 | 253, 284, 285, 300, 285, 254, 285 | 300 |
| 자산통계 재진입 | 407 | 394 | 439, 376, 361, 363, 422, 438, 394 | 439 |

검색은 중앙값 약 5%, 자산통계 재진입은 약 3% 줄었다. 지출통계 재진입의 시간 단축은 관측되지 않았다. 단위 검사로 중복 실행 감소는 확인했지만, 작은 시간 차이는 실행 변동이 포함될 수 있어 전부 특정 코드 변경의 효과로 단정하지 않는다. 변경 전 측정 도중 짧은 단위 검사가 15:28:45~49, 15:30:10~18 KST에 실행됐으며 표본을 삭제하지 않았다. 변경 후에는 같은 병행 검사가 없었다.

변경 전에는 자산통계 재진입만 기존 CI 프로필의 400ms 중앙값 기준을 초과했다. 변경 후에는 기준 조정 전에도 기존 CI 프로필로 33개가 모두 통과했다. 다만 로컬 통과는 이미 반복 실패한 다른 하드웨어의 GitHub CI나 실기기 성능을 보장하지 않는다. 별도의 엄격한 UX 기준에서는 메모·카테고리 저장 및 삭제의 기존 200ms 목표를 넘은 항목이 있고, 보고서에 이 판정도 유지한다.

## CI 기준의 한정 조정

사용자는 사용성을 유지한 최적화 후에도 달성하기 어렵다고 판단되는 기준의 완화를 승인했다. 두 실패 CI와 작은 로컬 개선 폭을 근거로 `github-hosted-v2`의 WebKit 네 항목만 다음과 같이 조정한다.

| 항목 | 중앙값 전 → 후 | 7개 중 6개 전 → 후 | 개별 최대 |
|---|---:|---:|---:|
| 첫 검색·검색 열기 포함 | 500 → 750ms | 800 → 1,000ms | 1,500ms 유지 |
| 지출·자산 통계 재진입 | 400 → 450ms | 600ms 유지 | 1,200ms 유지 |

검색은 과거 가장 큰 중앙값 739ms와 여섯 번째 표본 906ms를 고려했다. 통계는 과거 최대 중앙값 441ms를 고려해 500ms보다 좁은 450ms를 선택했다. 데이터·차트·전환을 줄여 이 차이를 없애기보다 CI 환경에 한정된 여유를 부여한다. 이것이 모든 향후 runner에서 통과를 보장한다는 뜻은 아니다.

기본 `ux-v2`, Chromium, Android, 통계 첫 진입·기간 변경, 다른 동작의 기준과 모든 개별 최대 제한은 유지한다. 원본 표본·준비 실행·실패 판정은 삭제하지 않으며 HTML의 CI/UX 전환에 각각 실제 기준이 표시된다. 기존 보고서는 기록 당시 기준을 사용한다.

## 검증·산출물

- 검색 4개 suite / 57개, 통계 5개 suite / 61개 집중 검사 통과.
- 성능 판정·통계·HTML 보고서 Node 검사 46개 통과. 새 기준 경계, 반복 초과, 단일 최대 초과, 기존 UX/Chromium 판정과 그래프 기준선을 검증했다.
- 후보 production 빌드와 실제 Emulator 기반 WebKit 7회 전체 경로 통과. 측정·기능 기대값을 변경하지 않았다.
- `web/performance-results/ux-safe-baseline/web.json`, `ux-safe-candidate/web.json`에 변경 전·후 원본을 보존한다. 후보 원본은 기준 조정 전 측정이다.
- `ux-safe-candidate/reviewed-budgets.json`은 원본 표본을 그대로 사용한 새 기준 재평가이며 재실행으로 간주하지 않는다. `ux-safe-candidate/web.html`은 이 결과를 표시한다.

Web 실행 코드만 변경해 main push의 Vercel Git 배포를 사용하며, 전체 CI 결과는 정확한 최종 push SHA로 별도 확인한다.

원본 CI 보고서와 단계별 비교는 `web/performance-results/ci-35186452895-analysis/`에 보관한다. 대형 측정 파일은 Git에 추가하지 않는다.
