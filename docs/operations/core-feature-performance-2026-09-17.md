# 핵심 기능 성능 테스트와 반복 측정

## 목적과 해석

실제 사용자 동작의 화면 반응과 서버 저장 확정을 구분하여 기록합니다. Web production build와 실제 Firebase SDK/Functions/Firestore Emulator 경로를 사용합니다. 앱 API 응답·시계를 가짜로 바꾸지 않습니다. Web 차트 애니메이션은 유지하고 Android OS 애니메이션 설정은 환경 정보에 기록합니다. 운영 계정·가계부 데이터에는 접근하지 않습니다.

이 값은 Windows 개발 PC에서 실행한 모바일 Chromium/WebKit 및 Android AVD의 기준선입니다. 실제 Android 휴대폰이나 iPhone PWA의 체감 시간, 운영 Firebase cold start 또는 인터넷 지연을 뜻하지 않습니다. WebKit의 모바일 설정과 standalone 감지는 iPhone의 하드웨어·OS 프로세스 수명까지 재현하지 않습니다.

기능마다 준비 실행과 본 측정을 구분합니다. 기본 본 측정은 7회이며 최소·중앙값·평균·최대·원본을 보존합니다. 7회 표본에 p95를 붙이지 않습니다. 실패를 빠른 성공으로 치환하거나 느린 표본을 임의로 제거하지 않습니다. 테스트가 중간에 실패한 실행은 보고서 전체 상태가 실패이며, 완료된 일부 표본만으로 기준선을 확정하지 않습니다. 다만 사용자 요청에 따라 이번 Android 홈 6회차의 50,666.6ms만 일반 성능 통계에서 제외하고 별도 진단 원본으로 보존합니다. 이는 이번 보고서에만 적용하며 이후 느린 값을 자동 제외하는 규칙이 아닙니다.

## 고정 데이터와 관측 방법

- 실제 Auth와 가구 생성·초대·가입 명령으로 3인 가구를 준비합니다. 36개월 × 월 60건, 총 2,160건의 합성 원장을 사용합니다.
- Web 자산은 12개 계좌/자산, 수동 평가 보유 항목 20개와 약 3년간 일별 assetSnapshots입니다. 실행 기준 날짜와 정확한 문서 수는 결과 JSON에 저장합니다. 시장 공급자 응답을 벤치마크에 섞지 않습니다.
- 자산 진입 시 백그라운드에서 읽는 외부 종목 카탈로그 HTTP 원천만 고정된 합성 manifest/gzip으로 제공합니다. 홈 최초·재실행 측정 뒤, 해당 Storage URL만 같은 origin의 테스트 HTTP 서버로 전환합니다. Firebase SDK의 요청·응답 처리, gzip/hash 검증과 제품 서비스 워커는 실제로 실행합니다. 앱의 Next production handler와 브라우저 HTTP cache를 유지하며 Auth·Functions·Firestore 요청은 대체하지 않습니다.
- 최초 홈 측정 뒤에는 제품이 예약한 서비스 워커의 실제 설치·활성화를 기다립니다. 이 준비 시간은 별도로 구분하며, 재실행은 활성 워커가 있는 같은 context의 새 문서에서 측정합니다. 강제 클릭이나 업데이트 배너 숨김은 사용하지 않습니다. 초기 활성화 후 배너가 남는지는 별도 진단 정보로 보존합니다.
- 로그인, 데이터 생성, 테스트의 관리자 REST 검증은 화면 측정 구간 밖에 있습니다. Functions는 준비 과정에서 이미 실행된 상태입니다.
- 이전 달 이동은 제품의 정상 인접 월 사전 조회를 허용합니다. 따라서 해당 context에서 처음 누른 이전 달이라도 서버 조회를 처음 시작하는 시나리오와 같지 않습니다.
- Web 클릭/입력 시작은 브라우저의 실제 이벤트 시각입니다. DOM 조건을 브라우저 RAF에서 관찰하므로 Playwright assertion의 polling 간격을 지연으로 더하지 않습니다.
- 차트는 새 데이터의 정확한 합계·대상 canvas drawing을 확인하고 100ms 동안 drawing이 안정되는지 관찰합니다. 통계에는 이 관찰 대기 100ms를 더하지 않습니다. 보고 시점은 이후 RAF의 paint 근사이며 물리 화면 표시나 Chart.js 내부 animation 완료를 직접 측정한 값은 아닙니다.
- 서버 저장은 해당 클릭 이후 시작한 명령의 성공 응답과 실제 canonical 필드를 확인합니다. 화면이 먼저 닫혔다는 이유로 저장까지 끝났다고 처리하지 않습니다.
- Native 창 표시에는 기존 production 지연 로그, 준비 상태에는 실제 View 조건, 닫힘에는 Activity lifecycle을 사용합니다. 서버 저장 확인은 인증된 조회의 왕복과 polling 오차가 포함되므로 Web callable 응답 수치와 직접 비교하지 않습니다.

## 실행과 CI

Web: `npm --prefix web run test:performance`

Android: Functions E2E 준비 후 실행 중인 AVD에서 `npm --prefix web run test:performance:android`.

반복 횟수는 `PERFORMANCE_SAMPLES`로 1~30을 지정합니다. 기본값은 7입니다. 측정끼리 또는 build/전체 테스트와 동시에 실행하지 않습니다. Android 기본 측정은 제품의 실제 Activity 종료 동작을 유지합니다. `native-firebase.mjs performance-isolated`는 종료된 Activity의 WebView를 테스트가 명시적으로 정리하는 별도 원인 비교용이며, 기본 CI와 기준선에는 사용하지 않습니다.

기존 CI의 `web-e2e` job에서 기능 E2E 이후 Web 성능 테스트를 실행하고, 이미 같은 job에서 만든 production build를 재사용합니다. Android는 기존 변경 범위가 실제 Native 검증 대상으로 판단된 경우에만 기존 emulator job에서 반복 측정합니다. 매 Web 변경마다 Android emulator를 강제하지 않습니다.

`quality-web-performance`, `quality-android-performance` artifact와 GitHub step summary에 결과를 남깁니다. 아직 CI 자체의 여러 실행 기준선이 없으므로 로컬 PC 시간으로 좁은 실패 임계값을 정하지 않습니다. 현재 CI는 실제 동작·정확한 데이터·완료 timeout을 검증하며 시간은 통계를 축적합니다. 편차를 확인한 뒤 기능별 허용 시간을 별도 결정합니다.

성능 시나리오는 Playwright 전용이며 Jest의 기존 102개 suite와 분리합니다. Vercel에는 성능 하네스·설정·생성 결과를 포함하지 않습니다. CI checkout에서는 모두 유지해 전용 실행기로 검증합니다.

원본 출력: `web/performance-results/web.json`, `android.json` 및 각 Markdown 표. 생성 출력은 Git에서 제외하고, 이번 측정의 확정 통계는 검토 후 아래에 기록합니다.

### 발견한 지연과 해석

- Android 홈 재실행의 원본 7회: 1112.6, 1051.6, 1159.5, 1461.0, 2170.9, 50666.6, 2752.0ms. 사용자 요청에 따라 6회차 50,666.6ms만 일반 성능 통계에서 제외했습니다. 나머지 6회의 중앙값은 1,310.3ms, 평균은 1,617.9ms, 최대는 2,752.0ms입니다. 제외 표본과 제외 전 7회 통계는 JSON의 `androidExcludedObservationDiagnostic`에 보존합니다. 이번 제외를 제품 성능 개선이나 장애 해결로 해석하지 않습니다.

- MainActivity에 WebView의 명시적 종료 처리가 없어서 이전 WebView를 정리하는 조건으로 별도 비교했습니다. 아래 진단은 기본 테스트나 CI 결과를 대체하지 않습니다.

- 후속 원인 분석에서 같은 회차의 52.1초 지연, 이전 WebView 누적, Firestore 연결 전 대기와 재시도를 관측했습니다. 이전 WebView를 명시적으로 정리한 추가 7회는 0.96~1.05초였습니다. 로컬 HTTP/1.1 Emulator에서의 반복 실행 결과이며 실제 휴대폰에서 같은 지연이 발생한다고 일반화하지 않습니다. 자세한 근거는 [Android 50.7초 원인 분석](android-home-outlier-analysis-2026-09-17.md)에 기록했습니다. 추가 진단은 위 일반 통계에 합치지 않습니다.
