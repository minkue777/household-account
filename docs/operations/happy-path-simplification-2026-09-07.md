# 3인 가구의 정상 사용 경로 단순화

## 범위

사용자 요청에 따라 평소 반복되는 잔액 갱신, 홈 화면 표시, 메모·카테고리 수정에 집중했다. 새 캐시·Queue·정책 인터페이스를 추가하지 않고 기존 코드에서 결과에 쓰이지 않는 작업과 중간 함수를 제거했다. 앞선 로컬 결제·지역화폐 변경은 보존했다.

## 변경

| 정상 사용 경로 | 이전 처리 | 변경 |
| --- | --- | --- |
| 홈에 표시할 유형이 선택된 뒤 지역화폐 잔액 갱신 | 매번 가구·설정과 전체 유형 목록을 읽음 | 가구·설정을 batch로 확인하고 선택이 있으면 전체 유형 query 2회 생략. read API 6→3회 |
| 홈 카테고리 요약 렌더 | 카테고리마다 전체 거래를 filter해 부모가 사용하지 않는 배열 생성, 미사용 건수 계산 | 카테고리 합계만 계산하고 클릭 시 category만 전달 |
| 홈 월 지출·예산 합계 | 같은 거래 배열을 두 번 순회 | 한 번 순회하며 두 합계를 함께 계산 |
| 메모·카테고리 수정 | 서비스와 두 내부 단계가 같은 거래를 3번 탐색 | 중간 함수를 제거하고 `begin`이 읽은 원본으로 version 계산. 3→2회 |

카테고리 상세 목록은 사용자가 선택한 뒤 `LedgerPage`가 최신 거래에서 계산한다. 따라서 요약 컴포넌트에서 미리 만든 배열이 필요하지 않았다. 카테고리 순서·합계·예산 표시·클릭 후 상세 동작은 동일하다.

낙관적 수정은 동일 호출 안에서 원본을 두 번 읽던 `beginUpdateInternal`을 삭제해 소스 12줄이 줄었다. 네트워크 요청은 기존대로 저장당 한 번이며, 저장 버전과 메타데이터 보존은 유지한다. 이 공통 경로를 사용하는 자산 편집도 기존 검사에 포함했다.

지역화폐의 기존 선택은 `HOME-002`에 따라 새 잔액이나 다른 유형 추가로 바뀌지 않는다. 실제 선택이 필요한 첫 등록에서만 유형을 확인한다. 최초 등록은 batch 적용으로 read API 6→5회이며, 목록 조회 단계가 선택 여부 확인 뒤로 이동한다. 비교 수치는 RPC 수로, 일반 갱신에서 읽는 문서 4개가 2개로 줄었다는 뜻은 아니다.

## 측정 근거

실제 변경 전후 `CategorySummary`를 ReactDOMServer로 렌더링해 비교했다. 합성 거래 300건·카테고리 5개에서 HTML이 완전히 같았다.

| 항목 | 전 | 후 |
| --- | ---: | ---: |
| 카테고리별 추가 filter | 5회 | 0회 |
| 거래의 category 필드 접근 | 2,100회 | 600회 |

실험 파일은 로컬 임시 디렉터리의 `happy-path-summary-benchmark-20260907.cjs`와 `.json`이다. 클라이언트 연산 횟수 비교이며 운영 로딩 시간이 몇 초 단축됐다는 측정은 아니다.

지역화폐는 실제 Application·Adapter의 기존 `local-currency-balance-read-efficiency` 검사로 정상 후속 갱신의 query 0·read API 3을 확인했다. 메모·카테고리 수정은 기존 서비스 검사에서 `current()` 2회와 실제 저장 응답·화면 상태를 함께 확인했다.

## 검토 판단

카테고리 설정 변경의 전체 catalog 중복 조회도 남아 있으나, 이번에는 매일 쓰는 홈·원장 경로를 먼저 줄였다. 정상 호출마다 필요 없는 전체 조회·배열 생성·중간 함수 제거를 우선했고, 드문 예외 대응용 구조를 추가하지 않았다.

## 검증

- Functions 품질 게이트: 321개 suite / 2,839개 통과. 별도 실행용 81개 skip. 타입·런타임 경계·architecture 38개·운영 빌드 통과.
- Web 전체: 98개 suite / 600개 통과. 정상 저장 경로의 기존 원장·자산 검사 47개를 포함한다.
- 실제 브라우저·Firebase Emulator의 로그인·지출 추가/수정/삭제 흐름 1개 통과. Web 운영 빌드와 정적 HTML 12개·CSP hash 25개·root worker 1개 검증 통과.
- 최종 빌드의 PWA 검사 2개 통과: 알림 편집 주소, CSP hydration, root worker 동작. 로그는 `happy-path-web-pwa-20260907.log`다.
- 실제 Firestore 통합: 13개 suite / 64개 통과. 첫 실행에서 동시 최초 지역화폐 등록의 목록 query가 Emulator의 `Transaction is invalid or closed` 오류로 실패했고, 제품 코드와 테스트 조건을 바꾸지 않은 재실행은 모두 통과했다. 이는 성능 개선 증거로 사용하지 않았다. 해당 목록 조회는 이미 선택된 정상 갱신에서 실행되지 않는다.
- 독립 리뷰로 사용되지 않는 콜백 인자, 금액 합산 순서, 최신 거래의 상세 선택, 낙관적 수정 버전 보존을 확인했다.

로그는 로컬 임시 디렉터리의 `happy-path-functions-gate-20260907.log`, `happy-path-web-tests-20260907.log`, `happy-path-firebase-integration-20260907.log`, `happy-path-firebase-integration-confirmed-20260907.log`에 남겼다. 이번 변경은 아직 커밋·push·배포하지 않았다.

Web 빌드가 지적한 제네릭 patch의 optional 타입을 명시적으로 좁힌 뒤 별도 TypeScript 검사와 전체 Web 테스트 600개·운영 빌드를 다시 통과했다. 최종 로그는 `happy-path-web-tests-final-20260907.log`, `happy-path-web-e2e-20260907.log`, `happy-path-web-build-final-20260907.log`다.
