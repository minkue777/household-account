# WebKit CI 성능 실패 진단과 후속 최적화

이 문서는 `eefe727f2e2e7412768570531eb1a43c1695df59`에서 반복된 WebKit 성능 기준 초과와 그 후속 변경을 기록합니다. 기능 오류와 시간 기준 초과, CI와 로컬 진단을 구분합니다. 기존 기준은 [v2 성능 보고서](core-feature-performance-v2-2026-09-17.md)에 있습니다.

최종 후보는 Chromium/WebKit 각 7회 측정에서 `ux-v2` 기준을 모두 통과했습니다. 이전에 실패한 GitHub runner의 재검증은 별도 CI로 확인합니다. 로컬 PASS를 CI 실패 해결이나 실제 iPhone 성능의 증거로 대신하지 않습니다.

## 기존 CI에서 확인한 실패

[CI 35171537404](https://github.com/minkue777/household-account/actions/runs/35171537404)는 기능 E2E 92개와 두 브라우저의 성능 시나리오 실행을 통과했지만, `github-hosted-v2` 시간 기준에서 실패했습니다. 33개 지표 × 2개 환경 × 본 측정 7회와 준비 실행 1회, 총 528개 표본이 완전하며 기능 실패 기록은 없습니다. 설정 페이지 이동 검증도 Chromium/WebKit 모두 통과했습니다.

## 측정 경계를 유지한 단계 진단

`PERFORMANCE_PHASE_DIAGNOSTICS=true`일 때만 다음 정보를 별도 `performance-phase-diagnostics` 첨부와 보고서의 `phaseDiagnostics` 배열에 기록합니다.

- 기존 DOM 판정 함수를 MutationObserver에서도 관찰한 최초 충족 시각과 관찰 출처
- 첫 rAF, 최대 rAF 간격, 관찰 프레임 수
- 관련 canvas별 최초 그리기, 모든 관련 canvas가 처음 그려진 시각, 마지막 그리기
- 기존 `endAt`과 판정을 실제로 확정한 `observedFinishAt`
- 추가 DOM 관찰의 호출 횟수와 실행 시간

기존 `durationMs`, 시작 이벤트, 종료 계산, 차트 그리기 안정 확인, 7회 기준과 원본 표본은 유지합니다. 단계 진단은 예산 판정용 표본에 합치지 않습니다. `firstDomMatchSource=start`는 조건이 동작 시작부터 참이었다는 뜻이므로 새 결과가 완성된 시각으로 해석하지 않습니다.

일반 지표는 브라우저의 실제 `click`/`input` 이벤트부터 측정합니다. 클릭 전 Playwright locator 자동 대기는 포함되지 않습니다. `options.ready()`의 locator 검증도 브라우저 측정값이 결정된 뒤 실행되므로 종료 시간을 늘리지 않습니다. `search.first-open`은 검색 열기 클릭부터 입력까지도 포함하는 별도 경계이며, 두 CI의 첫 입력 기준과 차이는 중앙값 약 19~21ms입니다.

차트는 마지막 그리기 이후 안정 상태를 100ms 관찰하되 그 확인 대기 전체를 측정 시간에 더하지 않고 기존 후보 paint 시각을 보고합니다. 그래프가 없는 화면도 rAF를 통해 DOM 이후 프레임을 관찰합니다. 따라서 DOM 조건 충족은 실제 화면 표시 완료와 동일하지 않으며, 빨리 충족된 DOM 시각으로 성능 종료 경계를 앞당기지 않습니다.

## 변경 전 로컬 WebKit 단계 진단

원본은 `web/performance-results/phase-baseline-2026-09-17/web.json`입니다. eefe727의 production Next.js build와 로컬 Firebase emulator에서 준비 실행 1회, 본 측정 2회를 수행했습니다. 환경은 Windows 10.0.26200, Ryzen 7 7800X3D, 논리 CPU 16개, Playwright 1.62.0입니다. 실제 iPhone이나 운영 인터넷 측정이 아니며 상태는 `DIAGNOSTIC`입니다.

## CSS 원인 분리 실험과 채택 범위

`paint-causal-diagnostic.json`은 로컬 WebKit에서 backdrop filter를 일시적으로 제거한 조건과 원래 조건을 비교한 진단입니다. 전체 조건 순서는 `baseline → without-backdrop → without-backdrop → baseline → baseline → without-backdrop`이며, 조건별 3회씩의 모든 값을 아래에 보존합니다. 이 파일의 iteration 0도 표본이며 임의로 제외하지 않습니다.

| 동작 | 원래 조건의 전체 표본 | backdrop 제거 전체 표본 | 중앙값 원래 → 제거 |
|---|---|---|---:|
| 카테고리 저장 | 104, 67, 68 | 85, 85, 63 | 68 → 85 |
| 검색어 변경 | 115, 133, 140 | 143, 158, 189 | 133 → 158 |
| 지출통계 3개월 | 238, 233, 223 | 208, 207, 208 | 233 → 208 |
| 지출통계 재진입 | 301, 300, 269 | 315, 268, 299 | 300 → 299 |

전역 backdrop 제거는 검색·저장에 일관된 개선을 보이지 않았으므로 채택하지 않았습니다. 지출통계 기간 변경만 세 표본이 모두 낮아졌고 중앙값이 25ms 줄었습니다. 이를 근거로 제품에서는 **StatsPage의 기간/합계, 월별 추이, 카테고리 비중 3개 패널의 `backdrop-blur-sm`만 제거**합니다. 패널 배경색·투명도·경계·그림자는 유지합니다.

이 실험은 표본이 3개이고 로컬 한 환경이며, 전역 CSS 조건을 바꾼 진단입니다. 세 패널만 바꾼 제품 후보에서도 25ms가 그대로 줄어든다고 보장하지 않습니다. 카테고리 저장 CI 실패의 단일 원인이 blur였다고 결론내리지 않으며, 실험용 전역 CSS 변경을 정식 성능 결과에 섞지 않습니다.

## 제품 변경과 유지하는 경계

### 검색어에만 의존하는 계산 재사용

`expenseService.createExpenseSearchMatcher()`에서 검색어 정규화, 정확한 카드 검색 토큰 해석, 공백 제거를 검색마다 한 번 준비합니다. 고정 카드 별칭 목록도 모듈 초기화 때 한 번 조회표로 만듭니다. 전체 검색과 SearchModal의 낙관적 projection 구독이 같은 matcher를 재사용합니다.

거래 필드는 매칭할 때마다 현재 값을 읽습니다. 따라서 수정한 메모·가맹점·카드 정보가 과거 결과로 고정되지 않습니다. 전체 기간·카드 별칭·마스킹·정확한 카드 검색·기존 ID·거래 표시 및 합계 의미는 바꾸지 않습니다. 날짜 필터, 숨은 재시도, 결과 일부를 잘라내는 처리는 추가하지 않습니다.

### 통계 부분 기간의 배열 참조 보존

`expenseStatisticsCache`는 같은 완료 원본에서 선택한 기간의 배열을 최대 4개까지 재사용합니다. `peek`와 비동기 `load`가 동일한 부분 기간에 새 배열을 각각 만들면서 같은 차트를 다시 그리게 하던 경로를 줄입니다. 전체 원본이 동일한 재검증이면 부분 배열도 보존하고, 실제 내용이 바뀌거나 확정된 수정이 반영되면 부분 배열을 폐기합니다.

조회 주체·가구·세션·원격 갱신 세대·변경 revision에 따른 격리, 기존 유효 기간, 최대 완료 범위 수, 서버 재검증 정책은 유지합니다. 부분 배열은 별도 원본을 복제하지 않고 기존 거래 객체를 공유합니다. 새로운 영구 저장소나 전역 데이터 캐시를 추가하지 않습니다.

### 통계 첫 범주 선택과 갱신 안내 레이아웃

현재 가구의 카테고리 목록이 준비되어 있으면 첫 렌더부터 실제 초기 선택 Set을 사용합니다. 기본 선택으로 차트를 그린 뒤 effect가 실제 범주 선택으로 바꾸는 추가 갱신을 줄입니다. 최초 선택은 예산이 설정된 범주 우선, 없으면 활성 기본 범주라는 기존 정책을 유지합니다. 가구·조회 주체·원격 갱신 세대가 바뀌면 선택 범위를 구분하며 사용자가 바꾼 선택은 같은 방문에서 덮어쓰지 않습니다.

`최신 내역 확인 중...` 안내는 나타나고 사라질 때 차트 위치가 이동하지 않도록 기간 라벨 아래 고정 높이 영역에 표시합니다. 읽기 실패 안내와 실제 새 데이터는 계속 반영합니다. 앞서 설명한 3개 패널의 blur 제거 외에 앱 전역 스타일이나 모달 표현은 바꾸지 않습니다.

## 최종 후보 검증

## 원본과 남은 검증

대형 측정 JSON은 Git에 추가하지 않고 실행 아티팩트로 보관합니다. 로컬 원본 위치는 저장소 기준 다음과 같습니다.

- `web/performance-results/ci-webkit-performance-2026-09-17.samples.json`: 앞선 두 CI 전체 결과, 로컬 단계 진단, CSS 비교 전체 24개 측정

원격 결과는 위 CI 실행 링크의 성능 아티팩트에서 확인합니다. 후속 CI에도 단계 진단을 기록하며 기존 실패와 같은 지표가 다시 초과하면 실제 DOM·그리기·프레임 구간을 확인합니다. 진단 표본을 정식 표본으로 대체하거나 느린 표본을 삭제하지 않습니다. 카테고리 저장의 CI 지연 원인은 아직 확정하지 않았습니다.
